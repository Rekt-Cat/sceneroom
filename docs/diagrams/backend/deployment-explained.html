SceneRoom: going live, explained

What we set up on 24 and 25 November 2026 to put SceneRoom on the internet, why each piece exists, what went wrong and how it was fixed. Click any box in a picture to jump to its explanation.

The one-sentence version: your editor already worked on your own computer, where one machine played every role; going live means giving each role to a computer on the internet and telling them how to trust each other.

The six pieces

Your browser

running
What it is
The editor itself. It draws the 3D view, keeps your project in the browser's database, and keeps its own copy of a shared scene.
In Unity terms
The game client: it can keep playing locally and sync when connected.

Vercel (web app)

running
What it is
Hosts the Next.js app: the pages and the /api routes. Each request starts a short function and ends.
Why we need it
Somebody has to send the editor to browsers and answer sign-in, project and invitation requests.
In Unity terms
The web backend and download server of a live game.
Cost and limits
Free Hobby plan, for non-commercial use. Its functions run in Singapore (sin1), next to the database (changed on 25 Nov 2026 from the US default, which nearly doubled the time of a database request).

Render (collab server)

running
What it is
Runs our own program apps/collab-server in a Docker container. It keeps connections open and relays edits.
Why we need it
Vercel's functions end after a request, so they cannot hold a live connection.
In Unity terms
A dedicated game server that relays state between players.
Cost and limits
Free. Sleeps after 15 idle minutes, wakes in up to about a minute, and its disk is wiped at every restart. That is why nothing important is stored on it.

GitHub

running
What it is
Two jobs: it stores the code, and it vouches for who a person is (an OAuth app named SceneRoom).
Why we need it
So we never handle anyone's password.
In Unity terms
Signing in with Steam or Google Play instead of making your own account system.

Neon (Postgres)

running
What it is
A managed database in Singapore. Holds accounts and also the shared scene documents.
Why we need it
Accounts need rules (who owns what, who may enter). The documents need a place that survives the collab server's restarts.
In Unity terms
The player database of a live game.
Cost and limits
Free: about 1 GB; the database pauses after 5 idle minutes, so the first request after a pause is slower.

Backblaze B2 (bucket)

running
What it is
Storage for files. A file is named by the SHA-256 fingerprint of its bytes.
Why we need it
Models and pictures are big, and the collab server's disk is wiped.
In Unity terms
The remote Addressables / asset bundle host.
Cost and limits
10 GB free. The code speaks the S3 standard, so Cloudflare R2 or AWS S3 would work by changing settings only.

Each step: what we did, what broke, how it was fixed

1

Prepare the code

done
Why we need it
A program that runs fine on your Mac needs extras to run on someone else's computer.
What we did
A Dockerfile (the recipe for a sealed box holding the server), a /health address the host can ask, file storage in a bucket (S3FileStore), a switch to turn off the old share links (LINK_SHARING=false), a Waking the server… message, and render.yaml.
In Unity terms
Preparing a headless server build and its launch settings.
Why link sharing is off
The old share links remember their owner in a small file on the server's disk. A wiped disk would forget a cancellation, so a cancelled link could work again. Accounts and invitations replace it.
2

Backblaze B2

done
What we did
You made a private bucket sceneroom-files and a key allowed to use only that bucket. check-files uploaded a tiny file, read it back and confirmed all five checks.
What went wrong
Secret keys were shown in screenshots and in the chat. A secret anyone has seen must be treated as public.
Fix
Replace the key: delete it, make a new one, and put it in Render and in apps/collab-server/.env. The master key was already replaced. The bucket key still needs replacing.
Lesson
Crop or hide secrets before sharing a screen. Use a key that can do only the one thing it is for.
3

Neon database

done
What we did
Created the project in Singapore, then built the tables from your computer with pnpm --filter @sceneroom/db migrate:remote.
Two addresses
Direct goes straight to the database (used by the collab server and for building tables). Pooled goes through a queue that shares connections (used by Vercel, which opens many short ones).
What went wrong
Your router's DNS could not look up Neon's name, so the command could not reach it.
Fix
Added the public DNS servers 1.1.1.1 and 8.8.8.8 on your Mac.
In Unity terms
A migration is like a versioned upgrade script for save data.
4

CI went red

done
What it is
CI is GitHub running our checks on a clean computer for every pull request.
What went wrong
Four account tests skip when sign-in is not set up, but their cleanup step still ran and tried to reach a database that job does not have.
Fix
The cleanup does nothing after a skipped test. Reproduced first on a fresh copy, then checked both with and without a database.
Lesson
Test the empty computer case: your own machine has settings and a database that CI does not.
5

Vercel build failed

done
What went wrong
Module not found: ./generated/client. Prisma writes database code into a folder that is not in git. Vercel reused cached packages, so the step that writes it never ran.
Fix
The database package now has a build step that generates it, and Turborepo runs that before the web app is built.
In Unity terms
A build that only works because the Library folder happened to exist, and fails on a clean machine.
6

Merge into main

done
What we did
The pull request from feature/collab-design was merged. main is the branch the live site and Render build from.
In Unity terms
Promoting a tested branch to the release branch.
7

Render

done
What we did
New, Blueprint read render.yaml and created the service; you typed the secret values. The log said: documents in Postgres, files in the bucket, link sharing off.
Checked from outside
Health answers; share route off; a file request without a pass is refused; only the web app's address may call it from a browser; live connections are accepted.
8

GitHub sign-in app

done
What it is
An OAuth app has a Client ID (public name), a client secret (its password) and the addresses GitHub may send people back to.
What we did
One app now has two redirect addresses: your computer and the live site.
Note
An earlier instruction to make a second app was based on an old one-address rule; GitHub now allows several.
9

Vercel settings

done
What we did
Eight environment variables, filled from apps/web/.env.vercel.
What went wrong
Saving twice said the names already existed (they did, from the first save). NEXT_PUBLIC_COLLAB_URL was refused as a secret. After adding it, the site still behaved as before.
Fix
That one is added as Config (it is sent to every browser, so it cannot be secret). Then redeploy Production without the build cache: names starting NEXT_PUBLIC_ are baked into the page when it is built.
In Unity terms
A value compiled into the player build, compared with one the server reads while running.
10

Checks by hand

to do
What we did
Not done yet. Sign in on the live site; open a project, Share, Put online with my account; make an invitation; open it on a second device; move things in both; import a model on one and see it on the other; wait 15 minutes and reopen.
Why a person

The secrets

Vercel's secrets

set
What it is
Read by the web app while it runs, except NEXT_PUBLIC_COLLAB_URL, which is read when the site is built and visible to visitors.
If one is missing
Accounts switch off: /api/me answers Accounts are not set up on this server.

Render's secrets

set
What it is
Read by the collab server when it starts. Saving a change restarts it.
If the database one is missing
The log names a .sqlite file instead of Postgres, and documents would be lost at the next restart.

COLLAB_SECRET

must match
What it is
A random 64-character password shared by the two servers. The web app signs a pass (token) saying who you are, which project and what you may do. The collab server recomputes the signature.
In Unity terms
A signed session ticket the game server verifies.
If they differ
Every connection is refused.

Files on your computer

local
What it is
Copies for local use. Git ignores any file named .env… except the examples.
Tidy up
Delete apps/web/.env.vercel now that Vercel has the values. Keep a copy of the secrets in a password manager.

The stages of a change

Commit and push

routine
What it is
A commit saves a step of work; a push sends it to GitHub.

CI checks

routine
What it is
verify checks formatting, lint, types, unit tests and a build, with a Postgres container. e2e drives a real browser.

Merge

routine
What it is
Only when both CI jobs are green.

Vercel

automatic
What it is
Builds automatically. Preview builds are test copies of branches; Production is sceneroom.vercel.app.

Render

automatic
What it is
Rebuilds from main when it changes (the Blueprint is synced).

Database changes

by hand
What it is
Hosts do not change the database. After adding a migration run migrate:remote before the code that needs it goes live.

If something goes wrong

You see Likely cause What to do
The page says it cannot reach ws://127.0.0.1:1234 The collab server was not deployed, or the site was built without its address Deploy on Render, set NEXT_PUBLIC_COLLAB_URL, redeploy
Accounts are not set up on this server A Vercel variable is missing or invalid, or the running build is older than the settings Check the eight names are Production, redeploy Production
GitHub shows a redirect_uri error The address is not listed in the OAuth app Add the exact callback address to the app
Connection refused in the editor COLLAB_SECRET differs between Vercel and Render, or you are not a member Set the same value on both; check the invitation
Waking the server… The free server was asleep Wait up to about a minute
Module not found ./generated/client in a build The database client was not generated Fixed: the build generates it
Can't reach database server from your computer Your DNS cannot look up Neon Use 1.1.1.1 and 8.8.8.8
A file does not appear for the other person The bucket settings on Render are wrong Read Render's log; run check-files with the same values

Words

Deploy
Put a program on a computer on the internet so others can use it.
Host
The company whose computer runs it.
Environment variable
A setting given to a program from outside its code, such as a password or an address.
Secret
A setting that lets someone act as you. Never in git, chat or screenshots.
Build
Turning the code into the thing that runs.
Redeploy
Build and start again, needed after a settings change.
Docker image / container
A recipe and the sealed box made from it, so the program runs the same anywhere.
Health check
An address the host asks to see whether the program is alive.
Bucket
A named space for files in object storage.
Migration
A saved change to the database's structure.
Pooled connection
Many requests sharing a few database connections.
OAuth
Letting GitHub confirm who you are without giving us your password.
Token
A signed pass: who you are, what you may open, until when.
CORS
A browser rule: a server lists which websites may call it.
WebSocket (wss)
A connection that stays open both ways; wss is the encrypted kind.
CI
Automatic checks run by GitHub on every pull request.
DNS
The internet's phone book: names to addresses.
