SceneRoom Architecture

What SceneRoom is made of, where each part runs, and how the parts talk to each other. Solid outlines are built and working today. Dashed outlines are planned, with the phase that builds them. Click a numbered box to jump to its explanation.

The whole system

1

Viewport

built
What it is
The 3D window. three.js draws 3D graphics in the browser using WebGL, and React Three Fiber lets us describe the scene as React components. Today it shows a cube on a grid with an orbit camera.
Unity comparison
The Scene or Game view window.
Why it is its own part
It is the only part that needs the graphics card, so it is loaded in the browser only. Later it will draw whatever is in the scene state (2) instead of a fixed cube.
2

Scene state

Phase 2 and 7
What it is
The data that describes the scene: a list of objects, each with a position, rotation, scale and material, plus what is selected. Zustand is a small library that holds this kind of shared data. In Phase 7 it becomes a Yjs document, which many people can edit at once.
Unity comparison
The scene file's contents held in memory, which is what the Hierarchy lists.
Why it is its own part
One single source of truth: the viewport and the panels both read from it, and every change goes through it. That is what lets undo and live sharing work.
3

Editor panels

Phase 3
What it is
The interface around the 3D view: a Hierarchy tree of objects, an Inspector for editing one object's values, a toolbar, and undo/redo with keyboard shortcuts.
Unity comparison
The Hierarchy and Inspector windows.
Why it is its own part
Panels only show the scene state and ask it to change. They contain no scene rules themselves, so the rules stay testable.
4

Shared types

package ready
What it is
The package @sceneroom/shared. It will hold the definition of what a scene looks like, as TypeScript types plus Zod checks that reject bad data. Right now it holds only a name constant and one example type.
Unity comparison
A shared assembly with the data classes that both the editor and the runtime use.
Why it is its own part
The web app and the collab server both import the same definition, so they cannot disagree about the shape of a scene.
5

Local save and files

Phase 5
What it is
Saving the scene as a JSON file, autosaving inside the browser (using IndexedDB, the browser's built-in database), and importing or exporting GLB files, the standard 3D model format for the web.
Unity comparison
Saving the scene and importing models, like dragging an FBX into the project.
Why it is its own part
It works without any server, so you can use the editor on your own before collaboration exists.
6

Static app on Vercel

built
What it is
The files our build produces (HTML, JavaScript, CSS), kept on Vercel and served through a CDN, a network of servers around the world that hold copies of them. It is live at sceneroom.vercel.app.
Unity comparison
The place a WebGL build is hosted. It only hands out files, and the game runs on the player's machine.
How it updates
Every push to main makes Vercel rebuild and republish. If a build fails, the previous version stays live.
7

API routes

Phase 6 and 8
What it is
Small pieces of server code inside the Next.js app that answer requests like "create a project", "list my projects" or "make an upload link". Vercel runs them only when called, which is called serverless.
Unity comparison
A small backend endpoint your game calls for things like cloud saves.
Why it is its own part
The server decides who may do what. The browser can be tampered with, so it is never trusted to enforce permissions.
8

Collab server

Phase 7
What it is
A Node.js program running in a Docker container. It uses Hocuspocus, a server built for Yjs documents. It keeps a WebSocket connection open to everyone editing a scene, passes each person's changes to the others, and saves the scene.
Unity comparison
A relay server for multiplayer, like Photon or Netcode.
Why it is separate
It needs long-lived connections, which suit an always-on server better than short-lived functions. I have not yet checked that against Vercel's docs. The host is undecided: Render, Koyeb or an Oracle VM, and the free-tier details must be re-checked first.
9

PostgreSQL

Phase 6
What it is
A database that stores users, projects, who belongs to which project, and the saved scene documents. We plan the hosted free tier from Neon and a library called Prisma to talk to it.
Unity comparison
The cloud save database behind a game.
Why it is its own part
It outlives any browser tab or server restart. Both the API routes (7) and the collab server (8) use it, through one shared package.
10

Object storage

Phase 8
What it is
File storage for big files: models, textures and thumbnails. We plan Cloudflare R2, which speaks the same language as Amazon's S3. The browser uploads straight to it using a signed link: a temporary address that our API creates after checking permissions.
Unity comparison
The server that hosts your downloadable asset bundles.
Why it is its own part
Large files never pass through our own servers, which keeps them small and cheap.
11

Login provider

Phase 8
What it is
GitHub or Google, through a standard called OAuth. The user signs in on their site, and our app only receives proof of who they are, never a password. Which library handles this on our side is still to be decided.
Unity comparison
"Sign in with Steam" or "Sign in with Google Play".
Why it is its own part
Storing passwords safely is hard, so we leave it to providers who do it for a living.

One edit, travelling between two people

This is the Phase 7 flow, so every box is dashed. Alice and Bob have the same scene open, and Alice moves the cube.

What if Alice and Bob edit at the same moment?

Yjs is built so that all copies end up identical without anyone waiting for a turn. Edits to different things, such as Alice moving the cube while Bob recolours the floor, both survive. If two people change the very same value at the very same moment, one of the two values wins and every screen shows the same winner. That is the rule Yjs documents for shared maps, and we will check it against the docs and test it in Phase 7.

How the code is organised

Why it is split this way

  • The browser does the drawing and gives instant feedback. Edits apply on your own machine first, so dragging never waits for a network round trip.
  • One source of truth for the scene. The viewport, the panels and the sharing all read from the same scene data, so they cannot drift apart.
  • The server never trusts the browser. Permissions are checked on the server, because anything in the browser can be changed by a visitor.
  • Shared code lives in one place. The scene definition is written once in packages/shared and imported by both the web app and the server.
  • Big files skip our servers. Uploads go straight to object storage through a signed link.
  • Scene rules stay separate from the screen. Rules live in plain TypeScript functions, and React components only show the result. That keeps them easy to test and to reuse in the collab flow.

Words on this page

WebGL
The browser feature that lets a page use the graphics card to draw 3D.
three.js
A JavaScript library for 3D graphics in the browser, built on WebGL.
React Three Fiber
Lets you write a three.js scene as React components.
Zustand
A small library for holding shared data (state) that several components read.
Zod
A library that describes what valid data looks like and rejects anything else.
Yjs
A library for data that many people edit at once. It merges everyone's changes into the same result.
CRDT
The technique Yjs uses: data structures designed so that all copies converge to the same state.
Hocuspocus
A ready-made server for Yjs documents.
WebSocket
A connection that stays open so the server and the browser can send each other messages at any time.
CDN
A network of servers around the world holding copies of your files, so visitors get them from a nearby one.
Serverless function
A small piece of server code that runs only when it is called, with no server for you to manage.
API route
A web address in our app that runs code and returns data, such as "list my projects".
Docker
Packages a program with everything it needs into a container that runs the same on any machine.
PostgreSQL
A database that stores structured records, such as users and projects.
Prisma
A library for talking to a database from TypeScript (an ORM).
ORM
Object-relational mapper: code that turns database rows into objects you can use in your program.
Object storage / S3
A service for storing files. S3 is Amazon's version, and many others copy its interface.
Signed link
A temporary web address that lets one specific upload or download happen without a login.
OAuth
The standard behind "Sign in with Google or GitHub". Our app learns who you are without seeing a password.
GLB
A single-file 3D model format widely used on the web.
IndexedDB
A database built into every browser, used here for autosave.
Monorepo
One repository that holds several related projects, such as the web app and the server.
