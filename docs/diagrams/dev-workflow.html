The path of an edit, step by step

Each card says what the part is, how it compares to something in Unity, what happens there, and what to look for if it breaks.

1

Claude Code

working
What it is
The AI assistant that runs inside VS Code. You describe a task in plain words. It reads files, runs commands and edits code, and asks you before anything risky.
Unity comparison
A teammate working inside your Editor who can edit scripts and run menu items. The difference: it remembers nothing between sessions except what it reads from files.
What happens here
At the start of a session it reads the repo files in box A, so it knows the plan, the rules and past decisions.
If it goes wrong
In a very long chat it can lose details. That is why facts live in files, and why it checks real versions with commands instead of guessing.
2

Edit a file

working
What it is
Claude changes a file with its Write or Edit tool. Each change is one tool call.
Unity comparison
Saving a script in your Assets folder.
What happens here
The change lands in your working folder only. Nothing reaches GitHub until you commit and push (box 5).
If it goes wrong
Easy to undo: git shows exactly which lines changed, and you can discard them.
3

Prettier hook

needs /hooks reload
What it is
A hook is a command that Claude Code itself runs automatically when something happens. This one runs after every successful Write or Edit (PostToolUse, matcher Write|Edit) and tidies that file's layout with Prettier, a formatter (what that means). It only touches files inside this project.
Unity comparison
Like an AssetPostprocessor: code that runs automatically when an asset changes. Here it reacts to Claude's edits.
What happens here
The hook receives the edited file's path as JSON, extracts it with jq, and calls Prettier on that one file.
If it goes wrong
The command ends with || true, so it never blocks you, which also means a broken hook fails silently. We tested it by hand, but it has not fired yet: the settings folder is new, so Claude Code needs /hooks opened once.
4

Local checks

passes
What it is
Three checks, started together by Turborepo (a task runner). lint asks "does this look like a mistake?" (done by ESLint). types asks "do all the values fit together?" (done by TypeScript's checker, tsc, after next typegen has written type definitions for our pages). build makes the real production version of the app (next build). More detail: the three checkers and what "types" means.
Unity comparison
Checking the Console for compile errors, then making a test build before you hand it over.
What happens here
Run from the repo root with pnpm lint, pnpm check-types and pnpm build. Turborepo works out the order and caches results. "FULL TURBO" in its output means it reused an earlier result.
If it goes wrong
A cached pass can hide a real failure. We hit this while reproducing the CI bug: the check replayed an old success until we forced a real run with --force.
5

Commit + push

working
What it is
A commit is a saved snapshot of the files with a message, stored on your Mac. A push uploads your new commits to GitHub. You push with GitHub Desktop.
Unity comparison
Checking in changes in version control, except a commit stays local until you push.
What happens here
Commits are small, with plain messages and no co-author line, as you asked.
If it goes wrong
Local commits can still be fixed. After a push to a public repo, assume everyone can read it, so secrets never go in (.env files are ignored).

GitHub repository

in sync
What it is
The online copy of the project at github.com/Rekt-Cat/sceneroom, branch main, with the full history.
Unity comparison
The cloud server your version control syncs to.
What happens here
Every push to main starts the CI workflow (7). Your other PC (8) gets the code from here.
If it goes wrong
The repo is public: anything pushed can be read by anyone.
7

GitHub Actions CI

green on b33fe6b
What it is
A workflow file, .github/workflows/ci.yml. On every push GitHub starts a fresh Linux machine, fetches your code and runs the steps below. It repeats your local checks in a clean place.
Unity comparison
A build server such as Unity Cloud Build that builds from a clean checkout, so "works on my machine" problems show up.
The eight steps, in order
  1. checkout downloads your repository onto the fresh machine.
  2. setup-node installs the Node version named in .node-version (24).
  3. corepack enable lets pnpm use the version pinned in package.json (12.18.0).
  4. install with a frozen lockfile installs exactly what pnpm-lock.yaml lists and fails if it disagrees with package.json.
  5. format runs prettier --check and fails if any file is not formatted.
  6. lint runs ESLint.
  7. types runs next typegen then tsc. This failed on the first run.
  8. build runs next build, a full production build.
If it goes wrong
A red cross on the repository's Actions tab means a step failed; open the step to read its log. Our first run failed at types: Next.js generates some files that git ignores, so a clean checkout did not have them. The fix (commit e798eac) generates them first.

Deep dives

Plain-words explanations of the parts that need more than a card: the three checkers, the Prettier hook, and what "types" means.

Three checkers, three jobs

Your code is looked at by three automatic checkers. They are easy to mix up because all three print warnings, but each one asks a different question. A fourth step, the build, then proves the whole app really compiles.

Tool The question it asks What it catches Unity comparison Changes your files?
Prettier "Is it laid out consistently?" Spacing, line breaks, quote style, aligned tables The editor's Format Document, with the same settings for everyone Yes, layout only. It never changes what the code means.
ESLint (the "lint" step) "Does this look like a mistake?" Typical examples: a variable that is never used, or a React Hook called in the wrong place Compiler warnings and Roslyn analyzers No. In our setup it only reports.
TypeScript (tsc, the "types" step) "Do the values fit together?" Passing two numbers where three are needed, calling something that does not exist The C# compiler's type checking No. --noEmit means check only.
Build (next build) "Does the whole app really build for production?" Problems that only show up in a full build Making a player build It writes build output into .next, which git ignores.
Prettier changes the layout 
before: const p={x:1,y:2}
after:  const p = { x: 1, y: 2 };
ESLint reports a likely mistake 
const unused = 5;
// typical report: defined but never used
TypeScript reports a mismatch 
type Vec3 = [number, number, number];
const position: Vec3 = [1, 2];
// error: needs 3 numbers, got 2

The ESLint and TypeScript lines are typical examples to show the kind of thing each tool finds. Which exact ESLint rules are on depends on the project's ESLint settings. All three run on your Mac and again in CI. Prettier is the only one that rewrites files.

What the Prettier hook really does

What Prettier is

Prettier is a code formatter: a program that rewrites the layout of a file (spaces, line breaks, quotes, semicolons, table alignment) into one consistent style. It never changes what the code means. It works on JavaScript, TypeScript, JSON, CSS, Markdown, HTML and more.

Why we use it

Everyone's files end up looking the same, nobody argues about spacing, and git diffs show real changes instead of whitespace noise. CI also runs prettier --check, so an unformatted file turns the build red. The hook makes sure Claude's edits never cause that.

Unity comparison: it is like Visual Studio's or Rider's "Format Document", except the settings are identical for everyone and it runs automatically.

A real example from this project

We tested the hook's command on a scratch Markdown file with extra blank lines and an uneven table. This is what came out:

Before 
# Test



| a | b |
|--|--|
| longer cell | x |
After Prettier 
# Test

| a           | b   |
| ----------- | --- |
| longer cell | x   |

What happens, in order

  1. Claude uses the Edit or Write tool on a file.
  2. If that tool call succeeds, Claude Code announces a PostToolUse event ("a tool just finished").
  3. The settings file has a hook whose matcher is Write|Edit, so Claude Code runs the hook's command in a shell. It sends the command a short JSON message about what just happened, through the command's standard input (its input pipe).
  4. jq, a small program for reading JSON, pulls the edited file's path out of that message.
  5. The shell checks that the path is inside the project folder. If it is not (for example one of Claude's memory notes), it stops. That is why the hook never touches files elsewhere.
  6. Prettier runs on that one file and rewrites it in place if its layout needs fixing.
  7. Output and errors are thrown away, and the command always reports success, so a formatting hiccup can never block Claude.

The command, piece by piece

Piece What it does
jq -r '.tool_response.filePath // .tool_input.file_path // empty' Reads the JSON message and takes out the edited file's path.
| { read -r f; ... } Passes that path to the next part, which stores it in a variable called f.
case "$f" in "$CLAUDE_PROJECT_DIR"/*) Only continues if the path starts with the project folder.
node_modules/.bin/prettier --write --ignore-unknown "$f" Runs the project's own Prettier on that file. --write rewrites it in place. --ignore-unknown skips file types Prettier does not know. Prettier also obeys .prettierrc.json and .prettierignore.
>/dev/null 2>&1 || true Discards all output and reports success even if Prettier failed.

What it does not do

It does not lint or type-check. It does not run when you edit a file yourself, or when a file changes through a shell command. It does not commit anything. Running pnpm format by hand formats the whole project, which is a separate command.

What "types" means: TypeScript, typegen and tsc

TypeScript and types

JavaScript lets you pass anything anywhere and only complains when the code runs. TypeScript is JavaScript plus labels that say what kind of value each thing is, such as "three numbers". A type check reads all the code and makes sure the values fit their labels, before anything runs.

Unity comparison: C# already works this way, and the compiler stops you from passing a string where a Vector3 is expected. TypeScript brings that safety to JavaScript.

tsc

tsc is the TypeScript compiler. We run it as tsc --noEmit, which means "check only, write no output files". Next.js does the real compiling itself during the build.

typegen

Next.js builds your pages from the files in src/app: a file named page.tsx or layout.tsx becomes part of the site. next typegen writes type definitions that describe those pages, for example LayoutProps, the type of what our root layout receives. They go into .next/types, plus a file called next-env.d.ts.

Unity comparison: like Unity generating a C# class from an asset, which the Input System can do from an Input Actions asset. The generated file is not hand-written and is not committed.

Why the order matters, and why CI failed

Our layout.tsx uses LayoutProps. If the generated file is missing, tsc says Cannot find name 'LayoutProps'. On your Mac the files existed from earlier builds. On GitHub's clean machine they did not, so the first CI run failed. The script is now next typegen && tsc --noEmit, and && means "run the second command only if the first succeeded".

Claude Code

One action Claude takes, such as reading a file, editing a file or running a command.
Hook
A command that Claude Code runs automatically when a chosen event happens.
PostToolUse
The event "a tool call just finished successfully".
Matcher
The filter that says which tools trigger a hook. Write|Edit means the Write tool or the Edit tool.
Standard input (stdin)
The channel a command reads data from. Claude Code sends the hook its message there.
JSON
A plain-text format for structured data, such as {"file_path": "..."}.
jq
A small command-line program for picking values out of JSON.
Prettier
A formatter that rewrites a file's layout into one consistent style.
ESLint
A linter: it scans code for likely mistakes and risky patterns.
Lint
An automatic scan for likely mistakes. The name comes from picking lint off clothes.
TypeScript
JavaScript with type labels, so mismatches are caught before the code runs.
Type check / tsc
The check that values match their labels, run by the TypeScript compiler (tsc).
typegen
A Next.js command that writes type definitions for your pages and layouts.
Build
Turning the source into the real, optimized version that gets deployed. Next.js writes it to .next.
Production build
The build meant for real visitors, as opposed to the dev server you use while working.
Turborepo
A task runner for projects with several packages. It orders tasks and reuses earlier results.
Cache / FULL TURBO
Turborepo reusing an earlier result when nothing changed. "FULL TURBO" means every task was reused.
pnpm
The package manager: it installs libraries and runs the project's scripts.
package.json
A package's ID card: its name, scripts and the libraries it needs.
Lockfile
pnpm-lock.yaml records the exact version of every library, so everyone gets identical ones.
Frozen lockfile
Install exactly what the lockfile says, and fail instead of changing it.
Corepack
A Node feature that makes pnpm use the version pinned in package.json.
Node.js
Runs JavaScript outside the browser. All our tools run on it.
.node-version
A one-line file naming the Node version this project uses.
fnm
A tool that installs several Node versions and switches between them per project.
Commit
A saved snapshot of the files with a message, stored locally.
Push / pull / clone
Push uploads commits to GitHub. Pull downloads new ones. Clone makes the first full copy.
Repository (repo)
The project folder together with its full history.
main
The name of the main line of history in the repo.
CI
Continuous integration: a robot that checks every push automatically.
Workflow
The file describing what GitHub Actions should do on a push. Ours is ci.yml.
Runner
The fresh machine GitHub starts to run the workflow. It is thrown away afterwards.
GitHub Desktop
A visual app for pushing, pulling and browsing changes.
.env file
A local file for secrets and settings. It is never committed.
Skill
A saved set of instructions Claude can follow, stored in .claude/skills/.
CLAUDE.md
A file in the repo that tells Claude the project's rules and commands.
