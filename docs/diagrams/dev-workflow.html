SceneRoom Dev Flow

How one edit travels from Claude Code on your Mac to a green check on GitHub, and what each part of the setup does along the way. Click a numbered box to jump to its explanation.

The path of an edit, step by step

Each card says what the part is, how it compares to something in Unity, what happens there, and what to look for if it breaks.

1

Claude Code

working
What it is
The AI assistant that runs inside VS Code. You describe a task in plain words. It reads files, runs commands and edits code, and asks you before anything risky.
Unity comparison
A teammate working inside your Editor who can edit scripts and run menu items. The difference: it remembers nothing between sessions except what it reads from files.
What happens here
At the start of a session it reads the repo files in box A, so it knows the plan, the rules and past decisions.
If it goes wrong
In a very long chat it can lose details. That is why facts live in files, and why it checks real versions with commands instead of guessing.
2

Edit a file

working
What it is
Claude changes a file with its Write or Edit tool. Each change is one tool call.
Unity comparison
Saving a script in your Assets folder.
What happens here
The change lands in your working folder only. Nothing reaches GitHub until you commit and push (box 5).
If it goes wrong
Easy to undo: git shows exactly which lines changed, and you can discard them.
3

Prettier hook

needs /hooks reload
What it is
A hook is a command that Claude Code itself runs automatically when something happens. This one runs after every successful Write or Edit (PostToolUse, matcher Write|Edit) and formats that file with Prettier. It only touches files inside this project.
Unity comparison
Like an AssetPostprocessor: code that runs automatically when an asset changes. Here it reacts to Claude's edits.
What happens here
The hook receives the edited file's path as JSON, extracts it with jq, and calls Prettier on that one file.
If it goes wrong
The command ends with || true, so it never blocks you, which also means a broken hook fails silently. We tested it by hand, but it has not fired yet: the settings folder is new, so Claude Code needs /hooks opened once.
4

Local checks

passes
What it is
Three checks run through Turborepo: lint (ESLint hunts for mistakes), types (next typegen then tsc, TypeScript's checker) and build (next build, a full production build).
Unity comparison
Checking the Console for compile errors, then making a test build before you hand it over.
What happens here
Run from the repo root with pnpm lint, pnpm check-types and pnpm build. Turborepo works out the order and caches results. "FULL TURBO" in its output means it reused an earlier result.
If it goes wrong
A cached pass can hide a real failure. We hit this while reproducing the CI bug: the check replayed an old success until we forced a real run with --force.
5

Commit + push

working
What it is
A commit is a saved snapshot of the files with a message, stored on your Mac. A push uploads your new commits to GitHub. You push with GitHub Desktop.
Unity comparison
Checking in changes in version control, except a commit stays local until you push.
What happens here
Commits are small, with plain messages and no co-author line, as you asked.
If it goes wrong
Local commits can still be fixed. After a push to a public repo, assume everyone can read it, so secrets never go in (.env files are ignored).
6

GitHub repository

in sync
What it is
The online copy of the project at github.com/Rekt-Cat/sceneroom, branch main, with the full history.
Unity comparison
The cloud server your version control syncs to.
What happens here
Every push to main starts the CI workflow (7). Your other PC (8) gets the code from here.
If it goes wrong
The repo is public: anything pushed can be read by anyone.
7

GitHub Actions CI

green on b33fe6b
What it is
A workflow file, .github/workflows/ci.yml. On every push GitHub starts a fresh Linux machine, fetches your code and runs the steps below. It repeats your local checks in a clean place.
Unity comparison
A build server such as Unity Cloud Build that builds from a clean checkout, so "works on my machine" problems show up.
The eight steps, in order
  1. checkout downloads your repository onto the fresh machine.
  2. setup-node installs the Node version named in .node-version (24).
  3. corepack enable lets pnpm use the version pinned in package.json (12.18.0).
  4. install with a frozen lockfile installs exactly what pnpm-lock.yaml lists and fails if it disagrees with package.json.
  5. format runs prettier --check and fails if any file is not formatted.
  6. lint runs ESLint.
  7. types runs next typegen then tsc. This failed on the first run.
  8. build runs next build, a full production build.
If it goes wrong
A red cross on the repository's Actions tab means a step failed; open the step to read its log. Our first run failed at types: Next.js generates some files that git ignores, so a clean checkout did not have them. The fix (commit e798eac) generates them first.
8

Second PC

not tested yet
What it is
Your other computer. It gets the project with a clone the first time and a pull afterwards.
Unity comparison
Opening the same Unity project on another machine from the cloud copy.
What happens here
The steps are in docs/SETUP-SECOND-PC.md: clone, fnm install, corepack enable, pnpm install. Real .env files and Claude's private memory notes are not synced.
If it goes wrong
Untested. The guide assumes macOS, so say so if the other PC runs Windows.

Supporting parts

A

Repo files Claude reads

in use
What it is
Four files that carry the project's memory: CLAUDE.md (rules and commands), docs/PLAN.md (where we are and what is next), docs/DECISIONS.md (why choices were made) and docs/WHAT-WE-USED.md (tools and libraries).
Unity comparison
The README and design docs every new teammate reads first.
What happens here
They sync through git, so a session on either PC starts from the same facts.
If it goes wrong
An out-of-date file misleads. Claude updates PLAN.md at the end of each step.
B

Skill: /update-what-we-used

needs /reload-skills
What it is
A skill is a saved set of instructions in .claude/skills/<name>/SKILL.md that Claude follows on request or when it fits. This one adds new tools to WHAT-WE-USED.md using the real installed versions.
Unity comparison
A custom Editor menu item that runs the same steps every time.
What happens here
Written and committed. The skills folder is new this session, so /reload-skills is needed once.
If it goes wrong
A skill is only instructions for Claude, unlike a hook that Claude Code runs by itself, so it can be skipped. Check the file afterwards.
