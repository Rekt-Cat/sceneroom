SceneRoom: the whole app

Every part of SceneRoom and how the parts connect: the editor in the browser, the web server, the collab server and the places data is kept. Click a numbered box to jump to its explanation. Below the figure there is one walkthrough per part, then the main journeys through the system (opening a project, one edit, going online, sharing, files, sign-in), where each kind of data lives, who may do what, and a glossary with Unity comparisons.

For how an edit travels from Claude Code to GitHub and Vercel, see dev-workflow.html. The script-by-script flow (what runs at start, then afterwards, per screen, with helpers and providers) is script-flow.html.

The parts, one by one

1

Screen

working
What it is
Everything you see and click: the top bar, the scene list on the left, the Inspector on the right, the tool dock, dialogs (Share, Project), the home screen with the project cards, and the sign-in button. These are React components. They only show state and call functions; they hold no scene logic.
In Unity terms
The Canvas UI and Inspector windows. A React component is like a MonoBehaviour that draws a panel from data and calls methods when a button is pressed.
Where in the code
apps/web/src/components/viewport/ (editor), components/home/ (home screen), pages in apps/web/src/app/.
Talks to
Reads and changes the scene state (2); the 3D view (3) is drawn inside it; the pages (7) deliver it; the sign-in button talks to sign-in (8).
2

Scene state

working
What it is
The single place the open scene lives while you work: every object, its transform, colour, modifiers, the selection, the undo and redo history, the open project and its scene tabs. Changes go through named actions (add a cube, move, extrude), each of which becomes one undo step. Stores also hold smaller things: edit mode, paint mode, panel widths, online status, who is here.
In Unity terms
A ScriptableObject-style shared data holder plus a command history (Undo stack) that everything reads from, so the UI never keeps its own copy.
Where in the code
apps/web/src/store/ (sceneStore.ts, projectStore.ts, editStore.ts, ...) built with Zustand; apps/web/src/collab/collabStore.ts.
Talks to
Calls the scene logic (4) for every real change; is drawn by the 3D view (3) and the screen (1); is saved by local save (5); is mirrored by the online layer (6).
3

3D view

working
What it is
Draws the scene in the browser with WebGL: shapes, imported models, characters, plants, lights, the ground grid, selection outlines, the move/rotate/scale handles, the edit-mode points and edges, painting, the four-view peek, other people's selections and pointers. It also handles camera controls, box selection and drag-and-drop of models.
In Unity terms
The Scene view and Game view camera of the Unity editor, with its gizmos and handles.
Where in the code
apps/web/src/components/viewport/Viewport.tsx and the controllers and objects next to it; meshEdit/, paint/, bake/ for the tools.
Talks to
Reads the scene state (2) and writes back through its actions; uses scene logic (4) for the maths (for example mesh editing, ray casting).
4

Scene logic (packages/shared)

working
What it is
All the real rules, written as plain TypeScript functions with no React and no three.js inside, so they can be tested alone and run on both the browser and the server. A function takes a scene and returns a new scene. Contains the scene shape (checked with Zod), undo history, primitives, lights, modifiers, mesh editing (extrude, bevel, loop cut, divide, simplify, UV unwrap), painting and baking maths, project and prefab rules, the scene-to-shared-document code, and per-person Undo.
In Unity terms
Your static utility classes and pure data classes (no MonoBehaviour), plus the data definitions. One copy, used by every part.
Where in the code
packages/shared/src/ (about 60 files, each with a test next to it). Key ones: scene.ts, sceneOps.ts, history.ts, sceneDoc.ts, selectiveUndo.ts.
Talks to
Used by the scene state (2), the 3D view (3), local save (5), the online layer (6) and the collab server (11).
5

Local save

working
What it is
Your work is kept in the browser first, with no account and no network. A project is saved a moment after each change (a burst of changes becomes one write). Big imported files (models, meshes, pictures) are stored apart, named by their SHA-256 fingerprint. You can also save the whole project to a .sceneroom file, open one, and export a .glb model.
In Unity terms
Like PlayerPrefs and the Library folder: saved on this computer only, until you export it.
Where in the code
apps/web/src/persistence/ (IndexedDB wrapper, project library, autosave, file storage), sceneFile/, export/.
Talks to
Reads the scene state (2) and writes to the browser's IndexedDB. Does not talk to any server.
6

Online layer

working
What it is
Turns the editor into a shared one. For each open scene it keeps a Yjs document (a shared data structure that merges two people's edits without losing either) in step with the scene state, keeps an offline copy of that document in the browser, and connects to the collab server. It also sends big files, shows who is here (names, colours, selections, pointers), enforces the courtesy lock one editor per object, and makes Undo take back only your own changes. A viewer's editor is read-only.
In Unity terms
Unity's networking layer (Netcode, Mirror) for a shared scene, with the difference that edits merge instead of one side winning.
Where in the code
apps/web/src/collab/ and packages/shared/src/sceneDoc.ts, selectiveUndo.ts.
Talks to
Reads and writes the scene state (2); talks to the live rooms (11) over a WebSocket and to the HTTP routes (12) for files and links.
7

Pages (Next.js)

working
What it is
The web server's job for the editor itself: it sends the app to the browser. Two pages exist: / (the home screen with your projects) and /p/<projectId> (the editor for one project). Everything inside the editor then runs in your browser, not on the server.
In Unity terms
The build of your game that gets handed to the player, plus the loader.
Where in the code
apps/web/src/app/page.tsx, apps/web/src/app/p/[projectId]/page.tsx, layout.tsx.
Talks to
Serves the screen (1). Later it will also serve the dashboard of shared projects (step M8e).
8

Sign-in (Better Auth)

working
What it is
Optional accounts. One route, /api/auth/..., handles Sign in with GitHub, the return from GitHub, sign-out and who am I. A signed-in browser carries a session cookie; the session itself is a row in our own database. If the six account settings are not set, the route answers 503 and the editor works as before, with no sign-in button.
In Unity terms
A login service you host yourself, like Unity's Authentication service but running inside your own project.
Where in the code
apps/web/src/server/ (auth.ts, accountsEnv.ts, session.ts), app/api/auth/[...all]/route.ts, button in components/home/AccountButton.tsx.
Talks to
Redirects to GitHub (10) and back; stores users and sessions in Postgres (16) through account code (9); answers the screen (1).
9

Account code (packages/db and the project routes)

working
What it is
The code that reads and writes the accounts database through Prisma: the schema, the role rules (permissionsOf, collabAccess), and the routes built on them. /api/projects lists yours or puts a project online with you as owner; /api/projects/<id>/members lists people, changes a role, removes someone or lets you leave; deleting a project is owner-only. POST /api/projects/<id>/token gives a member a one-hour collab token whose role follows theirs. Every route checks sign-in and the role on the server and validates input with Zod; a non-member gets no such project. Invitations (/api/projects/<id>/invitations, /api/invitations/preview and accept) make a person a member once, with only a hash of the link stored. When someone is removed, changes role or the project is deleted, this code tells the collab server to disconnect them. Next: documents in Postgres.
In Unity terms
The backend API of a live-service game: accounts, groups and the ticket office that hands out session tickets.
Where in the code
packages/db/; apps/web/src/app/api/projects/; rules in apps/web/src/server/projects.ts and collabToken.ts.
Talks to
Used by sign-in (8) for who you are; reads and writes Postgres (16); signs tokens the token check (13) accepts; the online layer (6) asks it for a token at every connect.
10

GitHub

outside
What it is
Not part of SceneRoom. It proves who someone is: you press the button, GitHub asks you to approve, and sends back a one-time code that our server exchanges for your name, email and picture. SceneRoom is registered there as an OAuth app named SceneRoom (local), with the return address http://localhost:3000/api/auth/callback/github. Its secret lives only in apps/web/.env.local.
In Unity terms
The platform login (Steam, Google Play) that tells you who the player is.
Where in the code
Settings in apps/web/.env.local (GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET); steps in docs/dev/SETUP-ACCOUNTS.md.
Talks to
Only sign-in (8) talks to it. The real round trip cannot be tested by a program, so it is checked by hand.
11

Live rooms (Hocuspocus)

working
What it is
The WebSocket part of the collab server. Each scene has a room named scene:<projectId>:<sceneId>. When someone joins, the server checks their token, loads the saved document (or an empty one), and relays every change to everyone else in the room. A viewer's connection is read-only: the server ignores what it sends. A message over the size limit closes the connection. A changed document is saved after two quiet seconds (ten at most); one over the size limit is not saved and is logged loudly.
In Unity terms
A dedicated game server that relays state between players.
Where in the code
apps/collab-server/src/createServer.ts, documentName.ts.
Talks to
Browsers' online layer (6) over a WebSocket; the token check (13); the SQLite file (14).
12

HTTP routes

working
What it is
The ordinary web requests the collab server also answers. /files/<projectId>/<fileId> stores and serves big files: the id is the file's SHA-256, so the server checks that the bytes match, refuses a file over the size limit, refuses a project over its quota, and refuses a viewer's upload. /share/<projectId> makes edit or view-only links (the first person to share becomes the owner, proven by a key that never leaves their browser) and /share/<projectId>/reset cancels all links and disconnects everyone who used them. POST /internal/disconnect is called only by the web app (signed with the shared secret, no CORS) to close one person's connections when they are removed. CORS headers let the web page call them.
In Unity terms
The content delivery and web-API side of a game backend (asset bundles, matchmaking links).
Where in the code
apps/collab-server/src/fileRoutes.ts, shareRoutes.ts, cors.ts, fileStore.ts, ownerStore.ts.
Talks to
The online layer (6); the token check (13); the files folder (15) and the SQLite file (14).
13

Token check

working
What it is
The gate every request passes. A link token holds the project, the role (editor or viewer), an optional expiry and a counter called the generation; it is signed with COLLAB_SECRET. The server recomputes the signature, checks the project matches the room or file, the expiry has not passed and the generation is still current (cancelling all links raises it). The secret is a random 64-character value in two git-ignored files, apps/collab-server/.env and apps/web/.env.local, and must match. The web app now signs these too: after it checks that you are a member of the project it hands out a one-hour token, and the editor asks for a fresh one at every connect.
In Unity terms
A signed session ticket, like a Photon auth token the server validates.
Where in the code
packages/link-token/src/linkToken.ts now in packages/link-token, shared by both servers.
Talks to
Used by the live rooms (11) and HTTP routes (12); later also by the web app that issues tokens.
14

SQLite file

working
What it is
Where the collab server keeps each scene's document between runs, plus the owner key fingerprint and the link generation of each project. One file (apps/collab-server/data/collab.sqlite by default), opened with Node's built-in node:sqlite, so there is nothing to install. When DATABASE_URL is set on the collab server the documents go to Postgres instead (table collab_document, step M8f) and this file only holds the owners of share links.
In Unity terms
A save file on the game server.
Where in the code
apps/collab-server/src/store.ts (SqliteStore; MemoryStore for tests).
Talks to
Written and read only by the live rooms (11) and HTTP routes (12).
15

Files folder

working
What it is
Big files (meshes, model files, pictures) as plain files, each named by its SHA-256 fingerprint. The same bytes can only ever be stored once, and a name can never be anything but 64 hex characters, so a request cannot point outside the folder. On a host without a lasting disk (a free web service) the same checks apply but the bytes rest in an S3-compatible bucket instead (Cloudflare R2, Backblaze B2 or AWS S3), chosen by the S3_* settings (S3FileStore).
In Unity terms
The Addressables / asset-bundle store.
Where in the code
apps/collab-server/src/fileStore.ts (FolderFileStore; MemoryFileStore for tests), folder from FILES_DIR.
Talks to
Written and read only by the HTTP routes (12).
16

Postgres (Docker)

working
What it is
The accounts database, running in a Docker container (docker-compose.yml, Postgres 17, 127.0.0.1:5432), with its data on the external drive. Tables: user, session, account, verification (Better Auth); project, project_member (role owner/editor/commenter/viewer), invitation (only a hash of its token), and collab_document (the shared scene documents, when the collab server is set to use Postgres). Docker Desktop must be open for it to run.
In Unity terms
The player database of a live game (accounts, inventories), as opposed to the world state.
Where in the code
docker-compose.yml, packages/db/prisma/.
Talks to
Sign-in (8) and account code (9) talk to it, and the collab server too, for the collab_document table only. Never the browser directly.

The main journeys through the system

A. Opening a project (local first)

Nothing here needs the internet, a login or a server.

  1. You open /. The pages (7) send the app; in the browser the screen (1) opens the browser's database and lists your projects with their small pictures (local save, 5).
  2. You click a project: the address becomes /p/<id>. The editor page starts and asks local save to restore that project. Until the restore is finished nothing is saved, so the starting scene (one cube) can never overwrite your real one.
  3. The restored project goes into the scene state (2): every scene, the open one, the prefabs. The 3D view (3) is loaded in the browser only (WebGL does not exist on the server) and draws it.
  4. Saving turns on: each change to the scene or to the list of scenes is written a moment later. Selecting objects and moving the gizmo mode are not saved. A picture for the home card is taken 4 seconds after opening and then at most every 30 seconds.
  5. If the id is not in this browser (a wrong or deleted link) the page says project not found and saves nothing. If the saved data cannot be read, saving is switched off on purpose to protect it.

B. One edit, offline

What happens when you, for example, drag an object with the move handle.

  1. The gizmo moves the 3D object directly while you drag (smooth, no React work). When you let go, one action in the scene state (2) writes the new transform.
  2. The action uses scene logic (4), which returns a new scene, and the history records one undo step with a label such as Move cube. The top bar's Undo button shows that label.
  3. The 3D view and the Inspector redraw from the new state. Local save (5) notices the scene changed and writes it to the browser after a quiet moment; the top bar goes Saving... then Saved.
  4. If you close the tab while a write is waiting, the page asks the browser to confirm, and it writes what it still has on the way out.

C. One edit, online (you and a friend)

Needs a collab server and a link. Steps 1 to 3 of journey B happen first, exactly the same.

  1. The online layer (6) sees the scene change and compares it with the previous scene. Only the differences are written into the shared document, in one transaction marked as yours. The browser's offline copy of the document is updated too.
  2. The provider sends the update over the WebSocket to the live rooms (11). The server relays it to everyone else in the room; if your connection is read-only (a viewer) it is ignored.
  3. In your friend's browser the update is merged into their document. Their online layer reads the changed objects out, checks them against the scene shape (Zod), and refuses anything invalid, then hands the scene to their scene state without adding an undo step for them. Their 3D view redraws.
  4. After two quiet seconds (ten at most) the server saves the document into the SQLite file (14). If it is over the size limit it is not saved, and that is logged as an error.
  5. If both of you change the same field at the same moment, the shared document picks one value consistently for both. If you change different fields of the same object, both changes are kept.
  6. If the connection drops, you keep working; your changes wait in the browser's copy and are sent when it comes back.

D. Sharing with a link (stage A, no account needed)

How the Share button works today.

  1. You press Share and choose edit or view-only, and how long the link works. The editor makes (once, in your browser) a random owner key and sends only its fingerprint to the HTTP routes (12). The first person to do this for a project becomes its owner; the key never leaves your browser.
  2. The server signs a token (13) holding the project, the role, the expiry and the current generation, and gives you a link containing it: the editor address plus the server and the token.
  3. Your friend opens the link. Their browser makes the project empty with the shared scene, remembers the token, connects, and the document fills it. A view-only token makes their editor read-only and the server ignores their changes even if they try.
  4. Cancel all links (owner key needed) raises the project's generation. Every older token is now refused, and the server closes the open connections of that project so they must connect again and are turned away.

E. Big files go by fingerprint

A scene object holds only the id of its file, never the bytes. The id is the SHA-256 of the bytes.

  1. You import a .glb or edit a big mesh. The bytes are stored in the browser under their fingerprint (local save, 5).
  2. The scene refers to the fingerprint. The uploader sends any file the open scene uses that the server does not have yet to HTTP routes (12) with your token. The server recomputes the fingerprint, compares the size to the limits and the project's quota, and stores it in the files folder (15).
  3. Your friend's scene mentions a fingerprint they do not have. Their storage asks the server for it when it is needed (with retries, because you may still be uploading), checks it, keeps it, and the model appears.
  4. A mesh edited by moving points (a sculpt stroke) is stored as a small difference from the earlier version, but is sent to the server as the whole mesh so the server never needs the chain.

F. Two people, one object: selection locks, edit locks and Undo

Online, an object belongs to the person who has it selected.

  1. Selecting holds. When you select an object, your editor adds its id to your holding record (the same small shared record as your name and pointer). Everyone else's editor sees it and treats that object, everything inside it and everything it is inside of as out of bounds.
  2. What others see: the object is highlighted in your colour with your name over it (Guest 237 is working on this), and the scene list shows your name on its row. They cannot select it (a message says who has it), no handles appear, and moving, renaming, hiding, locking, reparenting and deleting it are refused.
  3. Letting go: you deselect, or 30 seconds pass without a key, mouse button or wheel (your editor then clears your selection and tells you), or you disconnect, or you switch scene tab. The object is free at once for everyone.
  4. Two people at the same moment: the lower client number keeps the object and the other editor takes it out of its selection with a message.
  5. Viewers hold nothing and are never blocked. Without a connection to the collab server nobody's records arrive, so there are no locks, and the merge rule of the shared document applies.
  6. Edit points, Paint and Bake still announce their own courtesy lock, which now almost never matters because the object is already held.
  7. Undo online takes back only your own fields, and only the ones nobody else has changed since. It can still touch an object someone else now holds (a known limit).

G. Who is here

Presence is separate from the saved scene: it is never stored, and disappears with the connection.

  1. Each person publishes a small record: name (chosen in the Share box or a guest name), colour, which objects are selected, and the pointer position in the 3D world.
  2. Everyone else draws it: the avatars in the top bar, coloured boxes around objects other people selected, a ball for each pointer, and small coloured dots in the scene list. The pointer is sent at most a few times per second.
  3. Every received record is checked before use, because it comes from another browser.

H. Signing in with GitHub (accounts, built in step M8b)

Optional. It lets the system know who someone is; it does not yet control access.

  1. On the home screen the sign-in button asks /api/auth/get-session who you are. If accounts are not set up the route answers 503 and no button is shown.
  2. You press Sign in with GitHub. Sign-in (8) creates a one-time record in Postgres (16) and sends you to GitHub (10) with our client id and the return address.
  3. You approve. GitHub sends you back to /api/auth/callback/github with a code. The server exchanges it for your profile, creates or finds your user and account rows, creates a session row and sets a cookie.
  4. From then on, server code can ask who is signed in for this request from the session cookie. Sign-out deletes the session.

I. Online with your account, invitations and removal (steps M8c to M8e)

Instead of a link, the web app vouches for you. Needs a signed-in person and a collab server.

  1. You are signed in and press Share, then Put online with my account. The editor calls POST /api/projects (account code, 9), which makes the project in Postgres (16) with you as owner and remembers which scene is open (the one new members open first). Only a note online with my account is kept in your browser: no token is stored.
  2. To connect, the editor asks POST /api/projects/<id>/token. The server checks your session, finds your membership and signs a token for one hour that names you: read-write for owner and editor, read-only for commenter and viewer. A person who is not a member gets no such project and no token.
  3. The editor shows that token to the live rooms (11), which check it exactly like a link token (token check, 13). The token is asked for again at every connect, so a changed role or a removed member is noticed at the next connect.
  4. Invite someone: in the Share box the owner picks a role and a length (1, 7 or 30 days) and gets a link /invite/<secret>, shown once. Only a fingerprint of the secret is stored.
  5. Join: the other person opens the link. Signed out, the page says which project and role it is for and offers Sign in with GitHub; signed in, Accept invitation makes them a member with that role (once: the link is then used up) and opens the project online with the shared scene.
  6. The dashboard: the home screen lists every project you are a member of under Online projects, with your role.
  7. Removing someone: the owner removes a member (or changes their role, or deletes the project). The change is made in Postgres, then the web app sends a signed request to the collab server's /internal/disconnect. The server closes that person's connections; their browser reconnects, asks for a token again, and is refused. If the call cannot be made, the person is cut off at their next connect.

Documents can also be kept in Postgres: with DATABASE_URL set the collab server saves each scene's document in the collab_document table and loads it from there after a restart. Not built yet: rate limits (M9).

J. Deployment (step M9, live since 25 Nov 2026)

How it was set up: deployment-explained.html.

  1. Web app on Vercel (builds from GitHub). Postgres on Neon (accounts and scene documents). Sign-in through a second GitHub OAuth app with the real address.
  2. Collab server on Render's free web service (it sleeps when idle), as the Docker image built from apps/collab-server/Dockerfile. The host checks GET /health. After 15 idle minutes it sleeps and drops the connections; the first visitor waits up to a minute (the editor says Waking the server…) and everyone's work, kept in their browsers, is shared again when it wakes.
  3. Because that host has no disk that lasts: scene documents are in Postgres, the big files are in a Backblaze B2 bucket (an S3-compatible service; the collab server still checks every upload and download), and the old share-link routes are switched off (LINK_SHARING=false); accounts are the way in.
  4. Still open: the checks by hand on two devices, the limits (sizes, quotas, rate limits) and a custom address (optional).

Words on this page

Browser, server
The browser is the program on your computer that runs the editor. A server is another program, here or far away, that answers requests.
Next.js
The framework that builds the pages and the /api routes on the web server.
React component
A function that draws part of the screen from data. Like a Unity UI element driven by data.
Zustand store
A small shared box of data that components read and actions change. Like a ScriptableObject everything subscribes to.
three.js, react-three-fiber
three.js draws 3D in the browser (WebGL). react-three-fiber lets us describe the 3D scene with React components.
Zod
A checker for data from outside (files, messages, settings). It refuses anything that does not match the declared shape.
IndexedDB
The browser's built-in database for big data, kept on your computer.
WebSocket
A connection that stays open so either side can send at any time. Used for live changes.
Yjs, CRDT
A shared document type that merges simultaneous edits from many people without conflict, even after being offline.
Hocuspocus
The server and browser library that carries a Yjs document over WebSockets, with hooks for login and saving.
Awareness
The "who is here" record of Yjs. Never saved.
Token
A signed note saying who may enter which project and as what. Anyone can read it, nobody can forge it without the secret.
SHA-256 fingerprint
64 characters computed from a file's bytes. The same bytes always give the same fingerprint, so it works as the file's name.
OAuth, GitHub app
The standard way to let GitHub vouch for who someone is, without us ever seeing a GitHub password.
Better Auth
The library that runs the sign-in flow and keeps sessions in our database.
Prisma, migration
Prisma talks to Postgres with typed code from one schema file. A migration is a saved change to the database's structure.
Docker
Runs Postgres in a sealed box on your computer, so nothing is installed into the system.
Monorepo, package
One repository holding several programs and libraries: apps/web, apps/collab-server, packages/shared, packages/db.
