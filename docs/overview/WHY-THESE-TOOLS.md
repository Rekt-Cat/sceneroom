# Why these tools and not the others

For every tool in SceneRoom: what it is for, what else could have done the same job, why we picked this one, and when the
other one would be the better pick. A map of the layers: `docs/diagrams/overview/stack-map.svg`. The list of versions and where each tool is
used: `WHAT-WE-USED.md`.

**How to read the "why".** Reasons marked **(decision)** come from choices recorded in `DECISIONS.md` when they were made.
Everything else is general knowledge about the tools, not something measured in this project: it explains the usual
trade-off, and it can be out of date or arguable. "Not decided yet" means the choice is still open. For interviews: the
honest answer to "why X?" is usually "it fitted these needs, and Y would fit these other needs better", not "X is best".

## 4. Why not just one "do everything" product?

Services like **Liveblocks**, **Firebase** or **Supabase Realtime** would give live sync, login and storage with little code,
and for a business that wants to ship in a week they are a fine choice. We are not doing that, for three reasons:

1. **Learning.** The owner is learning modern web development; building the pieces teaches how they work, which is the aim
   of the project and the best interview material.
2. **Ownership.** Scenes and files stay on infrastructure we control and can move; no price change or shutdown can strand them.
3. **Fit.** A 3D scene has big binary files and a very particular edit model (modes, locks, per-user undo). Generic products
   cover the easy 80 percent, and we would still have to build the rest around them.

The cost, said plainly: more code to write and run ourselves, and the security of the server becomes our job.

## 5. Questions an interviewer may ask, with short answers

- **Why a CRDT and not a server that decides?** Offline editing and automatic merging come for free; no central referee
  has to reorder everyone's edits. The cost is some extra memory for the history the document keeps.
- **Why does the scene have a flat map of nodes?** Map entries merge field by field and can be moved without copying a
  tree; the tree for the panel is rebuilt from `parentId`. (`DECISIONS.md`)
- **Why are big files outside the document?** A document that holds megabytes of mesh data would be sent to every
  newcomer in full, slows everyone down and cannot be shared between scenes; files under a hash are stored once and cached
  forever.
- **Why Zustand next to Yjs and not Yjs alone?** The editor and its well over a thousand tests are built on pure functions over plain data;
  Yjs is the _transport and merge layer_ under it, not a replacement for the app's own state.
- **What would you change at ten times the size?** Move the collab server behind a load balancer with sticky rooms or a
  shared provider, store documents in Postgres with compaction, and move heavy work (bake, remesh) to workers.
